# GigBid: building a reviewable freelancer copilot

*Development note, updated 12 November 2026. Individual AI-4016 Assignment II project. The instructor has now supplied an example starter scaffold, but it contains no working GigSim service, persona corpus, or evaluation labels. The current workflow uses clearly labeled synthetic jobs and portfolio examples; an instructor-permitted Kaggle dataset supplies descriptive budget aggregates only. Every result below is an engineering check, not a claim about marketplace performance.*

A freelance bidding assistant has an awkward boundary. It can read a job, find relevant work in a portfolio, and draft a proposal, but it should not silently invent past experience or send anything on a freelancer's behalf. GigBid explores a workflow where an agent makes a recommendation and prepares an evidence-linked draft, then a person makes the final decision. The immediate research question is whether the workflow can preserve evidence, approval, and recoverable state across the path from a new job to a draft. It is too early to answer whether it produces better bids or hiring outcomes.

The surprising result from the first retrieval run was a perfect tie: four variants each found the right evidence on every synthetic question. That looked encouraging until I inspected the fixture. Four simple questions over six hand-written chunks could not distinguish designs. The useful finding was about measurement: selecting a production retriever from a clean-looking score would be unjustified, so the evaluation set needs harder cases and recorded provenance before the architecture choice is made.

## What the system does today

The current React screen shows a small inbox of synthetic jobs. A reviewer can start an analysis, inspect a bid, watch, or skip recommendation, and approve or reject a proposal draft. A second screen handles a synthetic client reply: the system identifies intent, looks up mock calendar slots, prepares a reply, and pauses before a synthetic message is recorded. The UI restores the latest run after a refresh when its checkpoint still exists. A FastAPI service exposes the job and workflow endpoints. LangGraph runs the bid and conversation state machines.

The job loader goes through a typed marketplace port. That port lets the local tests use a direct in-memory adapter while the container stack talks to a separate Marketplace MCP development server. In both cases, the jobs are synthetic. The adapter boundary matters because the course requires GigSim; once its actual contract and fixtures arrive, the simulator can implement the same port without changing the approval graph. The example ZIP supplies placeholders only. This is an integration seam, not a substitute for the prescribed simulator.

For a bid, three branches run in parallel. The analyst extracts requirements, the risk assessor flags suspicious features, and the fit matcher searches portfolio evidence. A decision node combines their outputs under configuration thresholds. A job post containing an instruction aimed at the assistant is skipped before drafting, regardless of its numeric risk score. The bid branch calculates a proposed price, writes a draft, runs a claim support and phrase check, and stops at a human approval interrupt. The reviewer sees the draft and reason codes before any synthetic marketplace write. Rejection ends without a draft. Editing the proposal blocks the write until its new claims receive another review. The current writer is deterministic so the safety path can be tested without hiding decisions behind a model call; it does not demonstrate language model quality.

The conversation graph starts from a synthetic client message. It classifies intent and extracts details, asks a local Workspace MCP mock for available interview slots, creates a candidate reply, and pauses for approval. Its calendar holds and email drafts are local SQLite records. The graph never sends a real email or a real marketplace message. The Workspace mock checks idempotency keys and rejects a key reused with a different payload, which prevents a retry from silently changing the intended action.

## MCP is the data boundary

The Portfolio MCP server exposes `search_evidence`, `get_case_study`, and `list_skills` tools, a `portfolio://case/{id}` resource template, and a screening-answer prompt. The bid fit node actually opens an MCP stdio session and calls the search tool. This is more than placing MCP in the architecture diagram: a separate MCP client successfully enumerated the tools and called the installable command. The current portfolio has only two clearly labeled synthetic examples. They cannot support claims about a real freelancer's history.

The Marketplace MCP development server exposes synthetic job reads and guarded draft or message operations. Workspace MCP holds mock slots and drafts. These servers give the graph explicit interfaces and make writes observable in tests. They do not establish integration with an Upwork account. I do not have an Upwork freelancer account for this project, so a live Upwork mode cannot be authenticated or verified. A future live adapter would require the user's own authorization and should remain behind the same approval boundary.

The Portfolio MCP command can be installed from the public GitHub release with `uvx --from git+https://github.com/FazalZamanKhan/gigbid.git@portfolio-v0.1.0 gigbid-portfolio-mcp`. A client runs it over stdio. The package currently demonstrates the protocol and synthetic evidence schema. A useful release for a real freelancer would replace that corpus with consented CV, project, and repository records, attach source identifiers and dates, and define how updates are indexed.

## Retrieval experiments before evaluation data

A proposal can sound persuasive while citing the wrong project. To investigate that failure, I built a retrieval harness that accepts a caller-supplied JSONL corpus and labeled queries. V0 uses fixed chunks and dense cosine similarity. V1 decomposes a query into requirements. V2 fuses dense and BM25 rankings using reciprocal rank fusion. V3 adds a cross encoder reranking stage. V4 can incorporate training-only outcome scores. V8 is a LangGraph corrective path that grades weak retrieval, re-queries, and can abstain. The harness reports Recall@5, MRR, nDCG@10, abstention, and p95 query latency. It records corpus and case file hashes and separates embedding index build time from query time.

A smoke run used a real BGE embedding model on six small synthetic chunks and four straightforward questions. V0, V1, V2, and V8 all returned the relevant item for each question. That perfect score is not evidence that any variant is superior: the fixture is tiny, easy, and hand written. The cross encoder could not be downloaded because the model host failed to resolve during the test, so V3 and V4 do not yet have measured model results. Unit tests with a deliberately simple reranker check their control flow only. No production retrieval choice follows from these checks. The default application still uses transparent keyword search over its two demonstration records.

The eventual comparison needs the provided personas, job types, split, and gold evidence identifiers. Outcome-aware features must be derived from training history only. Development and test outcomes must never leak into the retriever. I would run each variant against the same cases, report uncertainty intervals and subgroup results, inspect unsupported citations, and choose from the development split before touching the hidden test. Proposal quality needs a human rubric and an independently calibrated judge; retrieval scores alone cannot establish that a bid is honest or effective.

The instructor permitted several Kaggle datasets. I used asaniczka's 2024 Upwork job-postings dataset under ODC Attribution to calculate descriptive fixed-price budget references, with no raw job text in the repository. A reproducible script read 53,058 rows, removed duplicates, excluded hourly and missing or extreme budgets, and summarized 14,620 fixed-price posts into title-keyword categories. This adds market context but no fair-price gold label, client outcome, or live job feed. The [data card](DATA_CARD.md) records the filters, attribution, source hash, and limitations.

## Checkpoints, approval, and the failure boundary

A human interrupt is useful only if the decision survives a process restart. The default local API uses an in-memory checkpointer for quick development. The Docker development stack uses a Postgres LangGraph checkpointer. In an earlier container test, a synthetic bid reached the approval pause, the API restarted, and the same run resumed to create one approved draft. This verifies checkpoint recovery for that path. It does not prove exactly-once behavior if the process crashes after an external write but before checkpoint persistence. A durable outbox, unique marketplace operation identifiers, and a forced crash test are still required.

Reviewer Basic authentication protects the optional hosted preview when configured, and the public entry point serves the React build and API from one origin. This is a development preview architecture. It is not tenant-scoped authentication or a full security review. Credentials belong in the host's secret settings and, for course review, in a private Classroom comment. They should never enter the repository. The deployment blueprint uses Render Postgres; its free database expires after 30 days, so a preview on that plan needs migration or upgrade if grading continues beyond that period.

## What has been verified, and what remains

Sixteen Python and seven Playwright browser tests currently pass locally. They cover bid and conversation approval paths, MCP mock behavior, retrieval ranking control flow, API routing, reviewer authentication, setup persistence, rejection reasons, edited-draft blocking, outage messaging, and scam/injection skips. The React production build passes; the latest pushed revision is awaiting its CI result. The Portfolio MCP console command was installed locally and called through an independent MCP client. A previous Docker run verified the Postgres bid checkpoint after restart, but Docker stopped after the host reboot and the new conversation path has not yet had a container check.

The assignment asks for more than a working slice: official GigSim integration and outcome evaluation, a real model-backed agent and critic loop, memory, traces and cost accounting, a complete worker and container stack, a deployed application, a demo video, and a final measured R&D report. The instructor's example starter kit has arrived, but its simulator and evaluation assets have not. I will not substitute invented metrics for those inputs. The current interim PDF records engineering evidence and open questions. Any final report should identify the exact data revision, split, denominators, seeds, prompts, model versions, and failure examples so its claims can be reproduced.

The main lesson from the prototype is practical: an agentic proposal flow is easiest to reason about when evidence reads and external writes have narrow interfaces, and every write sits after an explicit approval point. The current tests support that engineering observation on synthetic examples. Whether GigBid helps a freelancer win suitable work, reduces unsupported claims at scale, or handles the course simulator reliably remains an empirical question for the official dataset and a complete implementation.
